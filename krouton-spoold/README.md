# krouton-spoold

A headless disc-burning server for Krouton. Krouton uploads a disc image over mutually-authenticated TLS, and
the server writes it to disc and streams progress back. The server runs on whatever machine has the burner
attached: macOS 12+ (Intel or Apple Silicon), Windows 10 (x86 or x64), or Raspberry Pi OS / Debian. See
[PLAN.md](PLAN.md) for the support plan and validation status.

```
Krouton (Swift, KroutonSpool package)                 burn box (macOS 12+, krouton-spoold)
┌──────────────────────────────┐   TLS 1.3, mTLS,    ┌────────────────────────────────────────┐
│ SpoolClient (actor)          │   pinned certs      │ main.rs / tls.rs   rustls, pin verifier │
│  Network.framework + CryptoKit│◀──────────────────▶│ session.rs         per-connection loop  │
│  Wire/Messages (golden-tested)│  framed binary     │ spool.rs           jobs + drive workers │
└──────────────────────────────┘   protocol v1       │ burner.rs          hdiutil -puppetstrings│
                                                     └────────────────────────────────────────┘
```

## Layout

| Path | What |
|---|---|
| `crates/spoold-core` | All protocol, state and burn logic, including the three platform backends. `std` only, **zero dependencies**, `#![forbid(unsafe_code)]`. 48 tests, including a decoder fuzz test. |
| `crates/krouton-spoold` | The binary plus a library: config, rustls, accept loop, `ring` SHA-256, free space (the only `unsafe`: one OS call per platform). Real-TLS end-to-end test in `tests/`. |
| `swift/KroutonSpool` | Swift package for Krouton: wire codec, messages, `SpoolClient`, identity/pin helpers. |
| `testvectors/frames.txt` | Golden frames generated by the Rust tests and checked byte-for-byte by the Swift tests. |
| `scripts/make-certs.sh` | Creates the server and client certificates and prints the pins. |
| `deploy/` | Example config, plus installers for macOS (launchd), Linux (systemd) and Windows (scheduled task). |
| `.github/workflows/ci.yml` | Tests on Linux, macOS and Windows; release builds for 7 targets; Swift↔Rust end-to-end test. |

## Security model

- **TLS 1.3 only, both sides authenticated, no CA.** Each side trusts the other's certificate by its SHA-256
  pin (hash of the DER). The server checks clients against `clients.pins`. Krouton checks the server against the pin
  it has stored. Possession of the private key is still proven, because rustls verifies the client's
  CertificateVerify signature.
- **To revoke a client,** delete its line from `clients.pins` and restart. **To rotate the server certificate,** let Krouton
  accept both pins (`serverPins` is a set) during the changeover.
- Session resumption is disabled, so every connection does a full handshake with certificate proof.
- **No hand-rolled crypto in production.** Pins and image hashes use `ring`. The core's own SHA-256 exists only so
  the core can be tested without dependencies, and a test checks it against `ring`.
- **Connection limits:** unauthenticated peers only ever hold one of `max_handshakes` slots, with a 5 s deadline,
  so they can't use up the `max_connections` session slots. Log lines escape control characters, so a client
  name can't forge log entries.
- **Job isolation:** a job can only be watched or cancelled by the client identity that submitted it. Other clients
  get "unknown job" and can't tell whether the job exists.
- **Image integrity:** the client declares the size and SHA-256 up front. The server writes strictly sequential chunks
  to `<id>.part`, hashes as it receives, and promotes the file to `<id>.img` only on an exact size and hash match.
- **Input hardening:** frames are capped at 516 KiB and the length prefix is checked before buffering. Every field
  is bounds-checked, trailing bytes are rejected, unknown flags and states are rejected, and image size is capped by
  config. Handshake, Hello and idle timeouts are enforced. Uploads are refused up front (`NoSpace`) if the spool
disk would drop below `min_free_gib`.

## Protocol (v1)

Frame: `u32 BE length | u8 type | payload`. Message definitions are in `msg.rs` and `Messages.swift`.

```
C→S Hello(version, client_name)          S→C Welcome(version, server_name, max_image_bytes, drives[id, name, jobs, burning])
C→S Submit(job, drive, size, sha256, opts) S→C Accepted(job), then Progress(job, state, %, ahead, total, message)…
C→S Chunk(job, offset, ≤512 KiB)*  C→S UploadDone(job)
C→S Watch(job)   C→S Cancel(job)   C→S Ping(n) → S→C Pong(n)   S→C Error(code, job?, message)
```

Job states: `Receiving → Queued → Burning → Done | Failed | Cancelled`. A job outlives the connection that submitted it.
After a disconnect, Krouton reconnects and sends `Watch`.

**Queue totals.** Every `Progress` carries `queue_ahead` (jobs that will burn on that drive first) and
`queue_total` (jobs queued or burning there). The server pushes an update to every waiting job whenever the line
moves: a burn finishes, a job is cancelled, or a new one joins. While a job is still uploading, `ahead == total`,
because it will join the back of the line. `Welcome` gives each drive's load before anything is submitted. If the connection drops during the upload, the job fails
and the partial file is deleted. Each drive has one worker, so jobs for the same drive queue up.

Any wire change must regenerate the vectors (`UPDATE_VECTORS=1 cargo test -p spoold-core`) and, if it is
incompatible, bump `PROTO_VERSION` on both sides.

## Build and deploy (burn box)

CI builds every target. Download the artifact for the box, or build locally with
`cargo build --release -p krouton-spoold --target <target>`. Make the certificates once on any Mac or Linux
machine:

```sh
scripts/make-certs.sh server basement-mini     # server.crt + server.key; prints the server pin for Krouton
scripts/make-certs.sh client macbook-pro       # macbook-pro.p12 for Krouton; prints a clients.pins line
```

| Burn box | Install | Config and certs go in | Logs |
|---|---|---|---|
| macOS 12+ (Intel: `macos12-intel` build) | `deploy/macos/install.sh ./krouton-spoold` (as the auto-login user) | `/usr/local/etc/krouton-spoold/` | `/Users/Shared/krouton-spoold.log` |
| Raspberry Pi OS / Debian | `sudo deploy/linux/install.sh ./krouton-spoold` (installs `xorriso`) | `/etc/krouton-spoold/` | `journalctl -u krouton-spoold` |
| Windows 10 x86/x64 | `deploy\windows\install.ps1 -Binary .\krouton-spoold.exe` (elevated) | `C:\ProgramData\KroutonSpoold\` | `spoold.log` there |

Each installer writes a starter `spoold.conf` with the right backend and drive, then tells you which files are
still missing. `krouton-spoold check --config …` validates everything: config, pins, certificate and key,
whether the burn tool is present, drive access and free space. It also prints the server pin. To exercise the
whole pipeline without a drive, set `backend = simulate`.

**Per-platform notes:**
- **macOS:** DiscRecording needs a logged-in session, so turn on auto-login.
- **Raspberry Pi:** power the burner through a powered hub.
- **Windows:** progress during the write shows as indeterminate for now (see PLAN.md, M4).

## Using it from Krouton

Add `swift/KroutonSpool` as a local package dependency, then:

```swift
import KroutonSpool

let identity = try ClientIdentity.fromKeychain(label: "macbook-pro")   // after a one-time importPKCS12
let endpoint = SpoolEndpoint(host: "basement-mini.local",
                             serverPins: [CertificatePin(hex: savedServerPin)!])
let client = SpoolClient(endpoint: endpoint, identity: identity)

let server = try await client.connect()
let job = try await client.submit(image: isoURL, driveID: server.drives[0].id,
                                  options: BurnOptions(verify: true, speed: 8))
for try await status in job.updates {
    // status.state, status.percent (nil = indeterminate), status.message → drive the UI
    // status.queueAhead / status.queueTotal → "2 ahead of you · 4 in queue"
}
```

Store `job.id` so Krouton can call `client.watch(id)` after a relaunch or a network blip.

## Known limits (v1)

See [PLAN.md](PLAN.md) for the milestones that address these.


- Jobs live in memory. Restarting the server drops them and clears the spool directory.
- An upload can't be resumed: after a disconnect mid-upload, the whole image is sent again.
- Cancelling during the burn kills `hdiutil`, which usually leaves the disc unusable. Krouton should warn before doing that.
- Drives are listed in the config, not discovered automatically.
- Windows reports no percentage while writing (IMAPI2 progress events need the planned native backend).
- Pins are matched against the hash of the full certificate, so re-issuing a certificate with the same key still changes the pin.
